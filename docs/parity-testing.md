# Проверки соответствия Minecraft Beta 1.7.3

## Статус

Это спецификация будущей системы проверок. Команды, схемы и сценарии ниже — контракт
для её реализации, а не описание уже существующего инструмента.

Заимствуем принцип Horizon: одинаковые входы → оригинальный Java-код и Rust-код →
сравнение результатов с сохранением доказательств. Проверки адаптируются к Beta 1.7.3;
современные механики, классы и формат данных Horizon к ней автоматически не относятся.

## Три уровня проверки

| Уровень | Пример | Что подтверждает |
| --- | --- | --- |
| Обычные тесты | Индексация чанка, границы буферов, обработка неверного NBT | Соблюдение заданных инвариантов |
| Сравнение с оригиналом | Последовательность RNG, изменение состояния после тика | Соответствие конкретному эталону в заданных случаях |
| Полная сцена | Игрок прыгает, ломает блок, сохраняет и открывает мир | Работу систем вместе в пользовательском сценарии |

Наличие только первого или второго уровня не даёт основания объявлять всю игру
совместимой. Нужны как проверки отдельных функций, так и их реального использования.

## Эталон и воспроизводимость

1. Положить принадлежащие пользователю оригинальные JAR клиента и сервера в локальное
   хранилище `.local/reference/` либо указать внешние пути конфигурацией.
2. При подготовке зафиксировать точную версию, SHA-256 обоих JAR, источник получения,
   Java runtime, ОС, библиотеки, параметры запуска и используемые патчи/инструменты.
3. Если оригинал инструментируется, хранить хеш исходного JAR, версию инструмента,
   описание преобразований и хеш подготовленного артефакта. Изменения для наблюдения
   не должны подменять исследуемую логику.
4. Каждый сценарий указывает, какой код является эталоном: Java API, клиентская
   одиночная игра, клиент в сетевом режиме либо сервер Beta 1.7.3.
5. Фиксировать входные данные, начальное состояние и порядок событий. Для исходного
   мира использовать отдельную рабочую копию на каждый запуск.
6. Java-адаптер вызывает настоящий исследуемый код. Переписанная в Java формула из
   Rust не является независимым эталоном. Для RNG первым эталоном служит настоящий
   `java.util.Random` зафиксированного runtime; это ещё не проверка всех RNG-вызовов игры.
7. Общие таблицы и код нормализации не должны маскировать одинаковую ошибку обеих
   сторон. Сохранять исходные выходы до нормализации.

Хеш оригинального JAR подтверждает воспроизводимость входа, а не полноту покрытия.
Зависимость от платформы и JVM документировать; межплатформенное побитовое совпадение
плавающей арифметики сначала проверить, а не объявлять предпосылкой.

## Минимальный runner

Предлагаемый интерфейс после реализации:

```text
python3 tools/parity/run.py list
python3 tools/parity/run.py rng --strict
python3 tools/parity/run.py storage --strict
python3 tools/parity/run.py movement --strict
```

Реализовывать группы по одной. Не показывать несуществующие группы как доступные.
`list` выводит реализованные сценарии и необходимые зависимости.
Runner запускает Java-адаптер и Rust-probe с одними входами, сохраняет stdout/stderr,
проверяет коды завершения, сравнивает результат и создаёт JSON-отчёт.
У каждого процесса есть тайм-аут; зависание считается `error`.

Статусы:

- `pass`: оригинал и Rust действительно выполнены, результаты соответствуют контракту.
- `fail`: выполненное сравнение обнаружило расхождение.
- `skip`: сценарий явно не запускался, причина указана.
- `error`: не удалось подготовить или выполнить сравнение.
- `not_implemented`: сценарий зарегистрирован в плане, но исполняемой проверки ещё нет.

В режиме `--strict` любой выбранный сценарий со статусом, отличным от `pass`,
даёт ненулевой код выхода. Неизвестное имя группы всегда является ошибкой.
В обычном режиме `fail` и `error` тоже дают ненулевой код; пропуски явно отражаются
в итоговом статусе и не называются успешным прохождением всего набора.

Минимальный состав отчёта:

```text
schema_version, suite, scenario_id, status, reason, scope
reference_side, reference_version, reference_jar_sha256
runtime_versions, platform, toolchain, adapter_sha256
rust_revision, rust_dirty, rust_binary_sha256, source_hashes
input_sha256, fixture_origin, seed, event_schedule, comparison_policy
case_count, mismatch_count, first_mismatch, duration_ms
reference_output_sha256, rust_output_sha256, log_paths
```

Неприменимые поля помечать явно. Например, для первого теста Java API оригинальный
игровой JAR не требуется. Незакоммиченный код идентифицировать хешами, одного Git SHA
недостаточно. Перед и после запуска проверять, что проверяемые входы и исходники
не изменились. Отчёт хранит ссылку на полный вход и полные выходы обеих сторон.

## План первых сравнительных сценариев

### 1. Java RNG и числовая совместимость

- Сначала `nextInt()`, `nextInt(bound)`, `nextLong()`, `nextFloat()`, `nextDouble()`.
- Фиксированные seed: `0`, `1`, `-1`, `42`, минимальный и максимальный `i64`.
- Для bounded RNG: степени двойки, соседние значения, большие допустимые bound,
  случаи отбрасывания кандидатов и отдельно ошибочные аргументы.
- Проверять длинную смешанную последовательность вызовов и повторный `setSeed`.
- Затем добавить `nextBoolean()` и `nextGaussian()`, включая сброс сохранённого
  Gaussian-значения при смене seed; политику сравнения transcendental-вычислений
  определить отдельно по выбранному runtime.
- Целые результаты сравнивать точно. Для `nextFloat`/`nextDouble` сравнивать битовое
  представление; диапазон `[0, 1)` проверять дополнительно.
- Следующим небольшим шагом: Java string hash по UTF-16, преобразования чисел,
  отрицательные координаты и используемый MathHelper.

Детерминированность двух экземпляров собственного RNG не доказывает совпадение Java.
Проверка диапазона также не подтверждает правильную последовательность.

### 2. Данные и сохранения

- Проверить чтение настоящих сохранений Beta: `level.dat`, заголовок `.mcr`, NBT чанка.
- Сравнивать координаты, массивы блоков, metadata, оба вида света и данные сущностей.
- Проверять распаковку nibbles, порядок осей, отрицательные координаты и границы регионов.
- После появления записи: Rust читает оригинальный мир; оригинал читает изменённую
  Rust копию; повторное открытие сохраняет данные и наблюдаемое поведение.
- `read(write(x)) == x` является полезным обычным тестом, но не заменяет проверку
  совместимости с оригинальным форматом. Два собственных адаптера могут иметь одну ошибку.
- Байты сжатых файлов могут различаться: сравнивать значимые распакованные поля.
  Перечень исключаемых служебных полей, например времени записи, задавать явно.

### 3. Движение и коллизии

- Малые сцены: ровная поверхность, стена, угол, край блока, плита/ступенька, лестница,
  лёд, вода, лава, паутина; затем сочетания этих случаев и границы чанков.
- Записывать исходную позицию, скорость, bounding box, направление камеры и ввод
  на каждом логическом шаге.
- Сравнивать позицию, скорость, коллизии, `onGround` и состояние падения по шагам,
  а не только итоговую точку. Исходные числа сохранять с достаточной точностью.
- Первоначально добиваться точного совпадения значимых вычислений. Если нужен допуск,
  зафиксировать единицы, абсолютный/относительный предел и причину; длительный дрейф
  и расхождение дискретных флагов допуском не скрывать.
- Отдельно проверить, что те же функции используются настоящим игроком в клиенте.

### 4. Генерация мира

- Сравнивать отдельно базовый рельеф, биомы, пещеры, поверхность и заполнение мира.
- Записывать seed, координаты, существующие соседние чанки и порядок generation/population.
  Сравнивать одинаковые расписания, а не только одинаковый seed.
- Сначала использовать последовательный режим. Параллельную реализацию проверять
  относительно зафиксированного порядка наблюдаемых изменений.
- Проверять блоки и metadata, выдавать координаты первого расхождения и карту различий.
  Визуальное сходство гор и деревьев недостаточно.
- Начать с нескольких соседних чанков около нуля и на отрицательных координатах,
  затем добавить границы биомов и большие координаты.

### 5. Игровые системы и сеть

- Добавлять инвентарь, рецепты, жидкости, освещение, редстоун и сущности по мере их
  реализации: входное состояние → последовательность действий/тиков → состояние.
- Проверять порядок событий, включая границы чанков и взаимодействие разных систем.
- Сетевые проверки: кодирование и чтение пакетов, частичные чтения TCP,
  последовательность входа, чанки, действия игрока и контейнеры.
- Помимо сравнения байтов выполнять оригинальный клиент↔Rust-сервер и
  Rust-клиент↔оригинальный сервер. Совместимость кодировщика и декодировщика между
  собой не доказывает совместимость с оригиналом.

### 6. Изображение и полные сценарии

- Фиксировать мир, позицию и ориентацию камеры, разрешение, настройки освещения,
  время суток, погоду, фазу анимаций и ресурсы.
- Сохранять снимки обеих сторон и изображение различий. Допуск по пикселям или
  метрике сходства определять для конкретной сцены и документировать.
- Учитывать различия драйверов и растеризации; визуальная проверка не заменяет
  проверки данных мира и симуляции.
- Пример сквозного сценария: открыть мир, пройти маршрут, добыть блоки, сделать
  инструмент, положить предмет в сундук, сохранить, перезапустить и проверить результат.

## Реестр покрытия и регрессии

По мере появления проверок вести `docs/parity-ledger.md`:

```text
система | поведение | сторона оригинала | источник | сценарии
статус | проверено отдельно | проверено в игре | известные расхождения
```

Не объявлять покрытие процентом от количества строк или количества тестов.
Знаменатель для любой оценки полноты должен быть определённым перечнем поведения.
Каждая найденная ошибка получает небольшой воспроизводимый сценарий.
Перегенерация эталонов — отдельная явная операция с описанием причины и просмотром diff.

## Запуск в CI

- Обычные тесты и законно распространяемые эталоны запускаются без приватных файлов.
- Live-сравнения с оригиналом требуют подготовленной среды и локальных артефактов.
  При их отсутствии показывать пропуск; обязательная live-задача завершается ошибкой.
- Разделять статусы обычных тестов, сохранённых эталонов и live-сравнений.
- Не публиковать JAR, ресурсы, декомпилированные исходники и секреты в логах/артефактах.
- Не усложнять CI до первого работающего локального сравнительного сценария.

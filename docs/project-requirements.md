# Проект: Minecraft Beta 1.7.3 на Rust

## Цель

Создать самостоятельную реализацию Minecraft Java Edition **Beta 1.7.3** на Rust.
Игра должна воспроизводить внешний вид, управление и наблюдаемое поведение
оригинальной версии, а производительность улучшаться по результатам измерений.
Это также эксперимент по проверке Gemini в разработке достаточно сложного проекта.

Разрабатываем небольшими законченными шагами. Сначала добиваемся проверяемого
соответствия выбранной части оригиналу, затем расширяем охват и оптимизируем.
Соблюдать этот файл при работе над любыми частями проекта. Роли и порядок совместной
работы описаны в [workflow.md](workflow.md); инструкции входа — в `AGENTS.md` и `GEMINI.md`.

## Принятые решения

- Целевая версия: **Beta 1.7.3**, без смешивания с Release 1.7.3 или Beta 1.8.
- Основной язык: Rust. Окно и ввод: `winit`; графика: `wgpu`; математика: `glam`.
- Первая среда разработки и проверки: Linux. Архитектура должна допускать
  последующую сборку под Windows без переписывания симуляции.
- Ресурсы оригинала на первом этапе читаются из локальной установки пользователя.
  Расположение задаётся настройкой; ресурсы и оригинальные JAR не добавляются в Git.
- Моды, загрузчики модов, шейдерпаки, улучшенная графика и поддержка других версий
  находятся вне текущего объёма работ.
- Genesis сейчас не используем. Работают две отдельные сессии: Codex и Gemini через
  Antigravity (agy), в отдельных папках Git worktree и ветках. Они могут одновременно
  выполнять независимые части задачи по заранее зафиксированному контракту.
  Отметки сессий изолированы по worktree; общая очередь карточек читается из Git и не блокирует независимые задачи.
- Gemini реализует движок; Codex готовит независимые эталоны, проверки, ревью и
  интеграцию. Вклад Codex в код движка учитывается отдельно. Дальнейшее автоматическое
  размножение агентов и смена моделей не входят в текущую схему.
- Java допустима в инструментах получения эталонных результатов. Конечная игра
  должна работать без JVM; сервер оригинала допустим как промежуточный стенд.

## Что означает соответствие

1. **Изображение и звук:** оригинальные текстуры и их анимация, модели, освещение,
   цвета биомов, прозрачность, туман, небо, частицы, интерфейс, звуки и музыка.
2. **Управление:** чувствительность и обработка мыши, камера, ходьба, прыжок,
   торможение, коллизии, подкрадывание, ступеньки, лестницы и жидкости.
3. **Игровая логика:** разрушение и установка блоков, инвентарь, крафт, инструменты,
   здоровье, предметы, сущности, жидкости, редстоун, погода и измерения этой версии.
4. **Мир:** загрузка и сохранение оригинальных миров, генерация ландшафта и
   заполнение мира при воспроизводимых начальных условиях.
5. **Сеть:** совместимость с протоколом Beta 1.7.3 в отдельном этапе разработки.

Не переносить механики последующих версий ради удобства реализации.
Характерные особенности и ошибки оригинала считаются частью поведения, пока
пользователь явно не согласовал отступление. Любое известное расхождение записывать.
Соответствие серверу не доказывает соответствие одиночной игре: для каждой проверки
указывать сторону и режим оригинала, с которым сравниваемся.

## Источники и их приоритет

Эталон — поведение конкретных оригинальных клиентского и серверного JAR Beta 1.7.3.
Для каждого фиксировать SHA-256, происхождение и среду запуска.
Документация и сторонние реализации помогают исследованию, но их результаты
не становятся эталонными автоматически.

| Источник | Назначение |
| --- | --- |
| `beta-wiki`, путь задаётся локальной конфигурацией | Локальная техническая документация по Beta 1.7.3 |
| <https://github.com/theorzr/mc173> | Основной пример Rust-реализации серверной логики |
| <https://github.com/ApfelTeeSaft/Minecraft-B1.7.3-CPP> | Дополнительный пример серверной архитектуры |
| <https://github.com/horizon-rust/horizon> | Идеи рендеринга, инструментов и сравнительных проверок |
| <https://github.com/MCPHackers/RetroMCP-Java> | Подготовка оригинала для исследования и Java-адаптеров |

В `beta-wiki` недописаны коллизии, построение геометрии, процедурные текстуры,
некоторые части генерации и редстоуна. Псевдокод движения отмечен как потенциально
неточный. Статус готовности стороннего проекта также не доказывает его точность.

Перед заимствованием кода фиксировать репозиторий, commit, файлы и лицензию,
сохранять требуемые уведомления. Отличать заимствованный код от написанного моделью.
Не добавлять в репозиторий оригинальные бинарники, ресурсы и декомпилированный код.

## Архитектурные требования

- Отделить симуляцию мира от графики, окна, ввода, сети и доступа к файловой системе.
  Ядро должно запускаться без окна для проверок.
- Хранить чанки и их данные компактно. Модель хранения должна корректно представлять
  исходный чанк 16×128×16, ID блоков, metadata, block light и sky light.
- Оригинальные форматы чтения и внутреннее представление отделять адаптерами.
- Физика персонажа должна воспроизводить Beta. Готовый универсальный физический
  движок не использовать как замену исследованию оригинального движения.
- Логический шаг отделить от отрисовки. Частота FPS не должна менять результат
  выполнения одной и той же последовательности логических шагов.
- В совместимых вычислениях сохранять значимые различия `f32`/`f64`, порядок операций,
  переполнение целых чисел, преобразования Java и порядок обращений к RNG.
- Собственный слой совместимости Java проверять независимо: RNG, текстовые seed,
  преобразования чисел, координаты и используемые математические функции.
- Не заменять функции оригинального MathHelper стандартными функциями без проверки
  влияния на результат. Использование `glam` само по себе точность не гарантирует.
- Начинать с понятной реализации на safe Rust. `unsafe` допускается для конкретной
  измеренной задачи с описанием инвариантов и проверкой корректности.
- Параллелить независимую подготовку геометрии, чтение и вычисления. Изменение порядка
  тиков, RNG и заполнения мира требует проверки поведения.
- Подключать зависимости по необходимости. При создании workspace фиксировать
  toolchain и `Cargo.lock`. Масштабные фреймворки и дополнительные сервисы не вводить
  без конкретной потребности текущего этапа.

Ориентир структуры по мере появления кода:

```text
crates/beta-core/        # данные, совместимые вычисления, симуляция
crates/beta-storage/     # NBT и McRegion
crates/beta-client/      # окно, ввод, рендеринг, звук, интерфейс
crates/beta-protocol/    # сетевой этап
tools/parity/           # запуск сравнения Rust и оригинала
tools/oracle/           # Java-адаптеры и подготовка эталона
tests/fixtures/         # небольшие проверочные входы и разрешённые эталоны
docs/                  # решения, прогресс, расхождения и методика
.local/                # локальные JAR, ресурсы, тестовые миры; вне Git
artifacts/             # отчёты, логи, снимки; вне Git
```

Это схема развития, а не требование немедленно создать все crates и каталоги.

## Этапы и критерии готовности

| Этап | Результат | Приёмка |
| --- | --- | --- |
| 0. Основа эксперимента | Минимальный Rust workspace, описание источников, фиксация эталона, первый runner сравнений | Один сценарий RNG реально выполняется в Rust и Java, формируется отчёт |
| 1. Данные мира | Чанк, NBT, чтение McRegion и минимальных данных мира | Из настоящего сохранения Beta правильно извлекаются блоки, metadata, свет и координаты, включая отрицательные |
| 2. Просмотр мира | Окно, свободная камера, атлас, геометрия чанков, сохранённое освещение | Зафиксированный участок оригинального мира корректно отображается; доступны сопоставимые снимки и время кадра |
| 3. Управление | Ходьба, прыжки, камера, коллизии, лестницы, жидкости, выбор блока, разрушение и установка | Записи ввода и состояния сравниваются с оригиналом по шагам; изменения видны в сцене |
| 4. Игровой цикл | Инвентарь, крафт, инструменты, здоровье, предметы, сохранение изменений | Короткий сценарий выживания продолжается после закрытия и повторного открытия мира в обеих реализациях |
| 5. Генерация и свет | Собственная генерация, заполнение мира и обновления освещения | Сравниваются данные для заданных seed, координат и порядка обработки, включая границы чанков |
| 6. Остальная симуляция | Мобы, жидкости, редстоун, транспорт, погода, Нижний мир и другие механики версии | Выполняются проверки подсистем и сценарии их взаимодействий; ведётся перечень оставшихся расхождений |
| 7. Сеть и завершение | Подключение к оригинальному серверу, собственный сервер, оставшиеся UI, звуки и эффекты | Проверены подключения оригинал↔Rust и полные игровые сценарии |
| 8. Оптимизация | Улучшены подтверждённые профилировщиком узкие места | Замеры воспроизводимы, проверки поведения продолжают проходить |

Измерять производительность с ранних этапов. Функции можно разбивать на несколько
задач; переходить к следующему этапу после описания результата и известных пробелов.
Сетевой стенд разрешено сделать раньше, если он нужен текущей проверке.

Подробная разбивка на пакеты, обязанности ролей и рубежи результата:
[roadmap.md](roadmap.md). Ближайший исполняемый контракт — REGION-001.

## Проверки по подходу Horizon

Подробная спецификация: [parity-testing.md](parity-testing.md).

Сравнительная проверка выполняет один набор входов в Rust и независимом оригинале,
после чего сравнивает наблюдаемые результаты. Обычные тесты и проверки диапазонов
полезны дополнительно; они не заменяют такое сравнение.

Обязательные принципы:

- Записывать происхождение каждого эталона. Нельзя создавать ожидаемый результат
  проверяемой Rust-реализацией или брать его из стороннего сервера без явной пометки.
- Числа, блоки и байты сравнивать точно там, где это требуется контрактом.
  Допуски для остальных величин обосновывать до проверки и указывать в отчёте.
- Для движения сравнивать состояние по шагам, для мира — сами данные,
  для изображения — фиксированную сцену, камеру и настройки.
- Различать состояния `pass`, `fail`, `skip`, `error`, `not_implemented`.
  Отсутствие оригинального JAR или адаптера не может давать `pass`.
- Проверка отдельной функции не означает, что она работает в реальной игре.
  Указывать точную область покрытия и отдельно проверять подключение к игровому циклу.
- Нельзя ослаблять проверки, увеличивать допуски или перезаписывать эталон ради
  прохождения реализации. Обоснованное исправление теста оформлять отдельно от
  исправления кода, с доказательством ошибки прежнего ожидания.
- Каждый этап добавляет только относящиеся к нему проверки. Не строить сразу
  огромный набор заглушек и не имитировать успешные результаты.

## Производительность

- Сравнивать release-сборку Rust с оригиналом на одной машине при одинаковой сцене,
  камере, разрешении, дальности, качестве, ограничителе FPS и состоянии мира.
- Фиксировать CPU, GPU, RAM, ОС, драйвер, Rust toolchain, JVM, аргументы запуска,
  версии и хеши бинарников, прогрев и число повторов.
- Собирать среднее время кадра, p95/p99 времени кадра, длительные задержки,
  время логического шага, загрузки мира, подготовки чанков и потребление памяти.
- Для памяти указывать конкретную метрику; учитывать всё дерево процессов оригинала.
  Холодную и прогретую загрузку измерять отдельно с описанием состояния кэшей.
- Сравнение неполной сцены помечать как ограниченное. Не заявлять ускорение всей
  игры по пустому миру, отключённой симуляции или уменьшенной дальности.
- Для оптимизации показывать исходный замер, изменение, повторный замер и проверку
  соответствия. Численный выигрыш заранее не обещать.

## Общий порядок работы

1. Прочитать этот файл, [актуальный прогресс](progress.md), [workflow.md](workflow.md)
   и относящиеся к задаче источники.
2. Прочитать `TASKS.md` и выбрать доступную карточку своей роли через
   `python3 tools/tasks.py next <role>`; её владелец и приёмка уже определены.
3. Реализовать его без несвязанных изменений и заранее объявленных готовыми заглушек.
4. Запустить относящиеся к изменению проверки. Для Rust выполнять форматирование,
   проверку сборки и подходящие тесты. Базовая команда workspace: `python3 tools/check.py`.
5. Записать результат в свой файл `docs/handoffs/codex.md` или `docs/handoffs/agy.md`.
   При интеграции Codex обновляет `docs/progress.md`: что готово, чем проверено,
   известные ограничения и следующая небольшая задача. Наличие файла не означает
   готовность функции.
6. Обновить свой role-status JSON и сделать коммит. Если доступна следующая карточка
   своей роли — продолжить её самостоятельно. Когда доступной работы больше нет,
   завершить занятую сессию и ответить пользователю по-русски: результат, проверки,
   ограничения и следующий шаг. Не придумывать новые этапы вне согласованной очереди.

Для оценки модели фиксировать model ID, настройки рассуждения, доступные инструменты,
время, использование токенов/стоимость при наличии данных, заимствования и ручную помощь.
Не придумывать отсутствующие метрики. Не менять модель незаметно.

При неизвестном поведении сначала исследовать оригинал и документацию. Если эталон
недоступен, явно записать непроверенное предположение и продолжить независимую работу.
Пользователь определяет спорные изменения цели и поведения; обычные обратимые
технические решения в рамках текущей задачи принимать самостоятельно.

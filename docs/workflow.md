# Совместная работа Codex и agy

## Внутренние агенты под управлением координатора

По указанию пользователя от 2026-11-08 Gemini заменён внутренними агентами.
Основной чат координатора остаётся на `gpt-6-luna` с reasoning `low`. Для
единственного рабочего агента отдельно выбирается `gpt-5.6-luna` с reasoning
`low`; не переключай основной чат на модель агента. Координатор назначает
конкретные карточки, разрешённые файлы и отдельный worktree.
Исторические названия
`codex` и `agy` остаются идентификаторами ролей очереди, а не названиями моделей.

Чтобы экономить лимиты, координатор запускает не более одного внутреннего
исполнителя одновременно. Работы ролей `codex` и `agy` выполняются
последовательно: координатор заканчивает свою подготовительную карточку,
передаёт исполнителю только нужный контракт и файлы, затем сам проверяет и
принимает результат. Отдельные агенты для runner, ревью и подзадач не запускаются;
ревью выполняет координатор. Исполнитель не делегирует дальше.

Координатор ведёт `codex/verification` и интеграцию в `main`. Исполнитель Rust
ведёт `agy/development`. Если исполнителю нужен другой worktree, координатор
назначает его явно; одновременно всё равно работает только один исполнитель.
Он не занимает чужие отметки сессий, не двигает чужие refs и не интегрирует в main.
Его рабочий каталог должен быть указан во всех командах. Координатор объединяет
конкретный коммит, сам проверяет результат и публикует собственные статусы.

Исполнитель сообщает координатору SHA, фактические проверки и ограничения. Завершение
агента само по себе не является приёмкой. Во время активного запуска координатор
ждёт отчётов и передаёт существенные результаты пользователю; после завершения
диалога постоянный фоновый наблюдатель не работает. Дополнительных агентов
назначает только координатор; исполнитель не делегирует самовольно.

## Два Git worktree

```text
173st/
  .repo.git/          # общие Git-объекты, refs и настройки
  .local/            # локальные оригинальные JAR и исходники для исследования
  codex/             # Codex, ветка codex/verification
  agy/               # исполнитель Rust, ветка agy/development
```

`main` содержит принятый результат. Интегратор — Codex. Каждый worktree содержит
весь проект, собственный index и рабочие файлы, но использует общую историю Git.
Редактирование и сборки выполняются одновременно; передача коммитов локальна.

В других окружениях пути могут отличаться. Репозиторий можно клонировать обычным
способом и создать worktree вручную. Два агента не должны редактировать один checkout.

## Локальная отметка сессии

В начале своей задачи:

```bash
# В папке codex/:
python3 tools/agent_session.py start codex

# Одновременно в папке agy/:
python3 tools/agent_session.py start agy
```

Отметка хранится в Git-каталоге конкретного worktree, а не в общем хранилище.
Обе сессии могут быть активны одновременно. Команда проверяет роль и ветку, но не
переключает ветку автоматически. Повторный запуск в том же worktree отклоняется.

После коммита, при чистой рабочей папке:

```bash
python3 tools/agent_session.py finish codex
# либо в agy/:
python3 tools/agent_session.py finish agy
```

Статус в своей папке: `python3 tools/agent_session.py status`.
Отметка — договорённость, а не технический запрет доступа. Не снимать чужую отметку
и не писать в соседнюю папку. При прерывании сначала выяснить состояние локальной задачи.

Самостоятельный выбор работы выполняется через `python3 tools/tasks.py next <role>`;
источник очереди — [`docs/tasks/queue.json`](tasks/queue.json).
Команды `python3 tools/tasks.py next codex` и `next agy` читают статусы из коммитов
веток соответствующих ролей. Файл чужого статуса в своём checkout может быть устаревшим.
После каждой карточки делать коммит и переходить к следующей доступной без ручного назначения.

Перед параллельной реализацией зафиксировать интерфейсы, входы, выходы и приёмку
общим коммитом. Приняты [RNG-001](tasks/RNG-001.md), [RNG-002](tasks/RNG-002.md),

[REGION-001](tasks/REGION-001.md); текущий контракт —
[WORLD-LOAD-001](tasks/WORLD-LOAD-001.md).
Если контракт нужно изменить, сначала договориться и обновить исходную ревизию
обоих агентов. Нельзя одновременно менять общие зависимости и ожидать бесконфликтный merge.

## Последовательный цикл

1. Координатор и исполнитель используют отдельные worktree; исполнитель начинает
   после завершения карточки, от которой он зависит.
2. За один раз запускается только исполнитель одной роли; роль `codex` готовит
   Java-эталон/runner, роль `agy` реализует Rust/probe по утверждённому контракту.
3. Исполнитель проверяет свою часть, обновляет свой status JSON и handoff, делает локальный
   коммит. Очередь самостоятельно обнаруживает готовность, передавать SHA вручную не нужно.
4. Координатор читает SHA результата из очереди, просматривает diff и объединяет именно этот
   коммит в своей папке. Незакоммиченные файлы соседнего worktree не используются.
5. Координатор сам выполняет проверки объединённого результата и сравнение с оригиналом.
6. При успехе интегрирует в `main`, обновляет общий прогресс и закрывает карточку.
   Следующий исполнитель запускается только после завершения текущего.

Исполнитель agy продолжает владеть своей веткой: интегратор не перемещает её refs и не выполняет
Git-операции в его папке. Интегрировать можно зафиксированный коммит, даже если agy
уже начал следующий независимый шаг, но отчёт обязан указать фактически проверенный SHA.

## Git и ресурсы

- `main` переключает и изменяет только Codex в своём worktree.
- Не пытаться checkout одной ветки в двух worktree.
- Не использовать force-push, reset или удаление worktree для обхода конфликтов.
- Общие refs и Git-настройки разделяются. Изоляция файлов не предотвращает смысловые конфликты.
- Не задавать двум сборкам общий `CARGO_TARGET_DIR`; `target/` остаётся отдельным.
- `artifacts/` и рабочие копии миров также отдельные для каждого worktree.
- `config/local.toml` задаёт общие пути `../.local/minecraft/` и `../.local/reference-sources/`.
- Общие оригинальные JAR, сохранения и источники используются только для чтения.
  Инструментирование и запуск миров выполняются на копиях в своих `artifacts/`.
- Prism-инстанция пользователя не является рабочей тестовой копией.
- `.repo.git/` нужен обоим worktree; его нельзя удалять или перемещать без перенастройки.

SSH-доступ GitHub проверен для `epik28`, origin использует
`git@github.com:epik28/173st.git`. Push для обмена локальными коммитами не требуется.
Токены и приватные ключи не сохранять в проекте и не выводить.

## Проверки и учёт вклада

`python3 tools/doctor.py` проверяет инструменты и локальные пути.
`python3 tools/check.py` — изоляцию сессий, fmt/check/clippy и обычные Rust-тесты.
Сравнительный runner RNG-001 реализован; новые группы добавляются по текущим контрактам.

В handoff указывать модель, настройки, исходную и итоговую ревизии, файлы, точные
команды и результаты, ограничения и полученную помощь. Успешная сборка каркаса не
подтверждает игровую совместимость. Вклад Codex в код движка учитывается отдельно.


## Подготовка общей очереди

При явном запросе пользователя подготовить следующий пакет интегратор может
инициализировать новые pending-записи обеих ролей в общем коммите контракта.
Выполненные статусы и доказательства чужой роли сохраняются. Это подготовка схемы,
а результаты выполнения по-прежнему пишет только владелец роли.
Синхронизация такого общего коммита в соседний worktree допустима при свободной
сессии, чистом дереве, ожидаемой ветке и fast-forward. Во время обычной работы
чужую ветку/папку интегратор не перемещает. Если сосед занят, дождаться его
самостоятельного обновления; несовместимая очередь не должна обходиться молча.

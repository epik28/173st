# Совместная работа Codex и agy

## Одна папка и отдельные ветки

Рабочая папка: `/home/andrew/173st`.

| Ветка | Назначение |
| --- | --- |
| `main` | Принятый общий результат, интегрирует Codex |
| `codex/verification` | Java-эталоны, runner, тесты и ревью |
| `agy/development` | Реализация движка Gemini |

Оба агента открывают одну папку. В ней одна активная ветка и один набор файлов:
переключение ветки действует на обе сессии. Изменения, сборки, тесты, коммиты и
переключения выполняются по очереди. Одновременное редактирование в этом режиме
не является независимой работой на двух ветках.

## Занятие сессии

Перед работой, пока папка чистая:

```bash
python3 tools/agent_session.py start codex
# либо, в сессии Gemini:
python3 tools/agent_session.py start agy
```

Команда атомарно создаёт запись занятия в `.git/173st-agent-session.json`, проверяет
чистоту рабочей папки и переключает на ветку роли. Если запись уже есть, запуск
отказывается переключать ветку. Посмотреть владельца: `python3 tools/agent_session.py status`.

После выполнения задачи и локального коммита, при чистом `git status`:

```bash
python3 tools/agent_session.py finish codex
# либо:
python3 tools/agent_session.py finish agy
```

Это договорённость между агентами, а не запрет доступа на уровне ОС. Обычные Git-команды
и редактор её не блокируют, поэтому оба агента обязаны соблюдать инструкции.
Занятая папка означает ожидание очереди через пользователя, а не запуск изменений
в обход отметки. При прерывании сессии сначала проверить её фактическое состояние;
не снимать чужую отметку автоматически и не терять незакоммиченные изменения.

## Цикл задачи и интеграция

1. Оба агента начинают задачу с согласованной принятой ревизии `main`.
2. В своей очереди Codex готовит Java-эталон и runner, Gemini — Rust-код.
3. Каждый выполняет проверки, обновляет свой handoff, коммитит и завершает сессию.
4. Codex в следующую очередь просматривает diff Gemini, объединяет результат в своей
   ветке и выполняет проверки на конкретном коммите, содержащем обе части.
5. Ошибки передаются Gemini вместе со входами и фактическими результатами.
6. После приёмки Codex вливает принятые изменения в `main`, обновляет общий прогресс
   и свою рабочую ветку. Следующую задачу агенты начинают после обновления своих веток
   до принятого `main` в своей очереди.

Ветки доступны локально, push для передачи коммита между этими сессиями не нужен.
Для MVP допустим обычный merge. Избегать перезаписи истории, force-push и reset.
Интеграцию выполняет один агент. При конфликтах сохранять смысл обеих частей и
проверять объединённый результат. Чужие незакоммиченные изменения не коммитить.

## Окружение и данные

- `python3 tools/doctor.py` — инструменты и локальные пути; GitHub-доступ не проверяет.
- `python3 tools/check.py` — Python-тесты занятия сессий, fmt, check, clippy, обычные Rust-тесты.
- Сравнительный runner появится задачей RNG-001; его пока нет.
- `.local/reference-sources/` — сторонние реализации для исследования, вне Git.
- `.local/minecraft/` — локальный клиентский JAR и сведения о происхождении, вне Git.
- `artifacts/` — логи, отчёты и рабочие копии миров, вне Git.
- `config/local.toml` — пути Prism и локальных данных, вне Git.

Сохранения пользовательской инстанции Prism не изменять: для тестов создавать копии.
Учётные данные использовать через Git credential helper или SSH agent, не сохранять
в репозитории и не выводить. Чтение GitHub не доказывает право записи.

## Учёт вклада

В handoff указывать задачу, модель и настройки, исходный и итоговый commit, файлы,
команды и результаты, ограничения, заимствования, помощь другого агента/человека
и доступные метрики времени и стоимости. Успешная сборка пустого ядра не означает
готовность игры. Результат совместной команды не равен самостоятельному результату Gemini.

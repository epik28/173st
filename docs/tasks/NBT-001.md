### Уточнение области эталона по исследованию C01/C03

Оригинальные `ij`/`nu`/`sp` реально проверены в client JAR с SHA-256
`af1fa04b8006d3ef78c7e24f8de4aa56f439a74d7f314827529062d5bab6db4c`.
Factory поддерживает только 0–10; тип 11 проверяется отдельно как wire extension.
Compound использует last-value-wins. Java writer нормализует NaN payloads и
записывает пустой список с типом Byte. Java reader принимает отрицательную длину
списка как пустой список, некоторые некорректные list types и одиночные surrogates.
Эти факты не меняют требований safe Rust API ниже: пустой список сохраняет тип,
неверные длины/типы отклоняются, `String` требует корректной пары surrogate.

Поэтому live parity считается только в общей области: типы 0–10, представимые
строки, без перечисленных расходящихся list cases. Native differences, IntArray
и Rust limits проверяются отдельными сценариями и не прибавляются к совпавшим
операциям. Правило «invalid отвергнуты обеими сторонами» относится к общей invalid
выборке; исходный Java reader не объявляется безопасным валидатором формата.
Сырые входные IEEE bits сохраняются в evidence; round-trip NaN проверяется по
фактическому DataOutput. Это уточнение происхождения доказательств, а не изменение
Rust API или подгонка оригинальных ответов. Полный список и команды —
`tests/fixtures/nbt/provenance.md`, `tools/parity/README.md`.

## Формат

Используются теги NBT типов 0–11: End, Byte, Short, Int, Long, Float, Double,
ByteArray, String, List, Compound и IntArray. Числа big-endian. Корневой тег —
именованный tag (End как корень запрещён). Compound завершается End. List содержит
тип элементов, signed Int length и ровно length payload без имён. Массивы содержат
signed Int length и bytes/values. Отрицательная длина, неизвестный тип, переполнение
размера, незавершённый Compound и trailing bytes после корня — ошибки.

Имена и строки кодируются тем же Java modified UTF-8 и двухбайтовой unsigned длиной,
которую использует `DataInput.readUTF`/`DataOutput.writeUTF`: NUL, двухбайтовые
последовательности, supplementary code points и malformed bytes должны иметь
явно проверенные случаи. Нельзя заменить это обычным Rust UTF-8 без доказательства
совпадения. API не обязан сохранять исходный порядок полей Compound при
десериализации, но writer должен быть детерминированным для одного дерева.

Размеры и глубина ограничиваются конфигурацией reader: default max depth 512,
max string bytes 65535, max collection elements 2_000_000, max total payload
64 MiB. Лимиты проверяются до выделения памяти. Ошибка не должна возвращать
частично принятое дерево.

## Rust API

Модуль `beta_core::nbt`, без внешних crates на первом шаге:

```rust,ignore
pub enum Tag {
    End, Byte(i8), Short(i16), Int(i32), Long(i64), Float(f32), Double(f64),
    ByteArray(Vec<i8>), String(String), List { element_type: TagType, values: Vec<Tag> },
    Compound(Vec<(String, Tag)>), IntArray(Vec<i32>),
}
pub enum TagType { End, Byte, Short, Int, Long, Float, Double, ByteArray,
                   String, List, Compound, IntArray }
pub struct NamedTag { pub name: String, pub value: Tag }
pub fn read_named(input: &[u8], limits: Limits) -> Result<(NamedTag, usize), NbtError>;
pub fn write_named(value: &NamedTag, limits: Limits) -> Result<Vec<u8>, NbtError>;
```

Фактические названия/конструкторы могут быть эквивалентными, но границы должны
сохранять signed widths и raw IEEE-754 bits. `List` пустой сохраняет объявленный
element_type; непустой список обязан иметь одинаковый тип всех элементов и не может
содержать End. `Compound` допускает повторные имена только если оригинальный reader
это подтверждает; сначала зафиксировать результат адаптером. `read_named` возвращает
количество использованных байт, writer не добавляет служебный trailer.

## Независимый эталон и probe

Codex C01 исследует настоящий NBT reader/writer в оригинальном Beta 1.7.3 client
JAR или подтверждённый Java NBT API, фиксирует class/method names, SHA-256 JAR,
reflection вызовы и отличия от формата. Если оригинальный класс недоступен,
это `blocked/error`, а ручная Java-копия формата не объявляется оригинальным
эталоном; независимый wire-format oracle при этом разрешён только как отдельно
помеченная проверка формата.

Проба `nbt_probe` принимает TSV `case_id<TAB>hex_bytes` и операции `encode:<hex>`
только после согласования C01; для первой live-проверки предпочтительнее corpus
готовых бинарных деревьев и round-trip, чтобы probe не содержал ожидаемых ответов.
Runner сохраняет raw bytes, parsed canonical tree, consumed length, stderr и
статусы `pass/fail/error/not_implemented`. Синтетические мутации меняют endian,
length, tag type, UTF-8 и один payload byte.

Корпус обязан включать все 12 типов, пустые/вложенные compound и list, границы
signed чисел, `-0.0`, infinities и NaN payload, NUL и supplementary Unicode,
пустые массивы, глубину/лимиты, отрицательные длины, truncation, unknown type,
trailing bytes, duplicate names и list с неверным элементом. Не менее 5000
операций/деревьев; отдельные invalid cases обязаны завершаться ошибкой с stderr.

## Разделение карточек и приёмка

Codex C01 — оригинальный адаптер, wire corpus и доказательство кодировки.
Codex C02 — runner, canonical comparator, invalid protocol и mutation checks.
agy A01 — safe Rust representation, reader/writer и limits; A02 — stdin/stdout
probe и ошибки. Codex C03 принимает только live-запуск обеих сторон.

Приёмка требует `python3 tools/check.py`, `cargo test --all-targets --locked --offline`,
прежние `rng`, `rng-extended`, `chunk` и новую `nbt --strict`; минимум 5000
валидных операций совпадают по canonical tree и consumed bytes, round-trip bytes
совпадают там, где writer детерминирован. Все invalid cases отвергнуты обеими
сторонами, а отсутствующий оригинальный класс/Java, timeout или build error не
становятся pass. Результат означает NBT parity, но не загрузку сохранения.
